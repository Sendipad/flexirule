# FlexiRule Automated & Daily Scheduled Audit System

Welcome to the **FlexiRule Daily Scheduled Architecture, Code Quality & Frappe Compatibility Audit** system.

## Overview

This directory (`reports/audit/`) stores the automated audit reports generated by daily scheduled runs and manual triggers via `.github/workflows/jules-task.yml`.

The primary goal of this audit system is to continuously ensure that **FlexiRule** adheres to:
- **Architectural Integrity & Consistency:** Preserving contract-driven design (`TRIGGER_TYPE_CONTRACT`, `contract_utils.py`, `FlexValueControl`, canonical conditions).
- **Native Frappe API Alignment:** Preferring native Frappe v15/v16 framework capabilities over custom duplication.
- **Code Quality & Security:** Detecting bugs, race conditions, permission bypasses, N+1 query patterns, and dead/legacy code.
- **Maintainability & Test Coverage:** Highlighting test gaps, flaky tests, and contract regressions.

## Audit Workflow Architecture

Daily scheduled audits run automatically via GitHub Actions:
- **Schedule:** Everyday at `02:00 UTC` (`0 2 * * *`).
- **Target Branch:** `develop` branch exclusively.
- **Jules Workflow File:** `.github/workflows/jules-task.yml`.
- **Manual Trigger:** Can also be launched on demand via GitHub `workflow_dispatch` or via `/jules` comments in issues/PRs.

## Audit Methodology & Tracking Rules

Every daily execution performs a progressive evaluation across 10 key audit dimensions:
1. **Python Backend & Action Handlers**
2. **Vue/JS Frontend & Rule Builder UI**
3. **RuleFlow Compilation & Evaluation Runtime**
4. **Contract Schemas & Metadata UI**
5. **Native Frappe API Compatibility (v15/v16)**
6. **Correctness, Concurrency & Security**
7. **Code Smells & Legacy Cleanups**
8. **Performance, Queries & Scalability**
9. **Test Coverage & CI/CD**
10. **Documentation Synchronization**

### Severity Categories
- **Critical:** Security vulnerabilities, permission bypasses, data corruption, or severe runtime crashes.
- **High:** Functional bugs, race conditions, significant performance bottlenecks, or broken contracts.
- **Medium:** Framework API duplication, missing test branches, code smells, or unhandled edge cases.
- **Low:** Minor code cleanliness, outdated comments, or naming inconsistencies.

### Incremental Report Management
- Daily runs check existing reports in `reports/audit/` to track finding status (`Open`, `Verified`, `In Remediation`, `Resolved`).
- New findings are appended under new dated report files (`AUDIT_REPORT_YYYY-MM-DD.md`).
- Resolved issues are tracked across reports to prevent duplicate finding reports.
