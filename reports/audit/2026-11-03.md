### Finding FR-DATA-002: Active Version Concurrency Row-Locking
1. **ID and Severity**: `FR-DATA-002` | **MEDIUM**
2. **Category**: Data Integrity / Concurrency
3. **Location**: `flexirule/ruleflow/doctype/rule/rule.py:1874-1896` (`validate_single_active_version`)
4. **Evidence**:
   ```python
   existing_active = frappe.get_all(
       "Rule",
       filters={
           "base_rule_name": self.base_rule_name,
           "is_active": 1,
           "name": ["!=", self.name],
       },
       pluck="name",
       limit=1,
   )
   ```
   `frappe.get_all()` issues a standard `SELECT` without pessimistic row locking (`FOR UPDATE`).
5. **Impact**: Concurrent activations of sibling versions within the same rule lineage can race past validation, leading to multiple active versions simultaneously.
6. **Root Cause**: Reliance on read-uncommitted / snapshot read in `frappe.get_all` without explicit locking.
7. **Native Frappe Alternative**: Frappe Query Builder `.for_update()`:
   ```python
   rule = frappe.qb.DocType("Rule")
   existing_active = (
       frappe.qb.from_(rule)
       .select(rule.name)
       .where((rule.base_rule_name == self.base_rule_name) & (rule.is_active == 1) & (rule.name != self.name))
       .for_update()
       .run(pluck=True)
   )
   ```
8. **Version Compatibility**: Supported in Frappe v15 and v16 via PyPika-based Query Builder.
9. **Recommendation**: Replace `frappe.get_all` with Frappe Query Builder `for_update()` in `validate_single_active_version`.
10. **Tests**: Add concurrency test in `flexirule/ruleflow/tests/test_rule_versioning.py`.
11. **Confidence**: Confirmed (Open).

### Finding FR-PERF-001: N+1 Query Pattern in Child Table Mappings
1. **ID and Severity**: `FR-PERF-001` | **HIGH**
2. **Category**: Performance
3. **Location**: `flexirule/ruleflow/core/action_handlers/document_action.py:517-584` (`_apply_table_mappings`)
4. **Evidence**: Child table mappings iterate over rows and call `doc.append(table_field, row_payload)` sequentially. Each `doc.append` invokes document model validation and metadata field checks.
5. **Impact**: Severe execution slowdown when mapping large datasets (hundreds of rows) into child tables.
6. **Root Cause**: Iterative row-by-row append instead of batch assignment.
7. **Native Frappe Alternative**: Prepare list of row dictionaries and invoke `doc.set(table_field, row_list)` or `doc.extend(table_field, row_list)`.
8. **Version Compatibility**: Frappe v15 and v16 native `Document` methods.
9. **Recommendation**: Accumulate row payloads in memory and apply via `doc.set(table_field, rows)` when `reset_value` is true.
10. **Tests**: Add benchmark regression test in `test_document_action.py`.
11. **Confidence**: Confirmed (Open).

### Finding FR-SEC-004: Background Worker Session User Privilege Escalation
1. **ID and Severity**: `FR-SEC-004` | **HIGH**
2. **Category**: Security / Authorization
3. **Location**: `flexirule/ruleflow/core/permissions.py:174-184` (`can_ignore_permissions`)
4. **Evidence**: `can_ignore_permissions` checks `frappe.session.user`. When rules are processed by a background worker (e.g. RQ queue), `frappe.session.user` defaults to `Administrator`, inadvertently bypassing role validation checks.
5. **Impact**: Background jobs executing actions with `ignore_permissions` pass role verification regardless of the user who scheduled the job.
6. **Root Cause**: Reliance on ambient `frappe.session.user` rather than context-propagated triggering user.
7. **Native Frappe Alternative**: Store `initiating_user` in rule execution context and use `frappe.set_user(context.get("initiating_user"))` during background task execution.
8. **Version Compatibility**: Frappe v15 and v16.
9. **Recommendation**: Explicitly pass initiating user in background job parameters and enforce role gates against that user.
10. **Tests**: Add background task permission test in `test_permissions.py`.
11. **Confidence**: Confirmed (Open).

### Finding FR-FE-002: Double Stringification of `condition_json` Payload
1. **ID and Severity**: `FR-FE-002` | **MEDIUM**
2. **Category**: Frontend / Serialization
3. **Location**: `flexirule/public/js/flexirule/rule_builder/stores/useRuleStore.js:320-335`
4. **Evidence**: When serializing rule data before form save, `condition_json` is serialized via `JSON.stringify()` even if it was already stored as a JSON string by child components.
5. **Impact**: Can lead to escaped quotes `\"` and nested string encoding in database columns, complicating backend parsing.
6. **Root Cause**: Defensive stringification without checking `typeof value === "string"`.
7. **Native Frappe Alternative**: Use standard Frappe JSON parser / serializer helpers.
8. **Version Compatibility**: Client-side JavaScript.
9. **Recommendation**: Check `typeof condition === "string" ? condition : JSON.stringify(condition)`.
10. **Tests**: Verify with `tests/frontend/flexirule/rule_builder/utils/stable_serialization.test.mjs`.
11. **Confidence**: Confirmed (Open).

### Finding FR-BACK-001: Missing Compile-Time Allowed-Root Validation for Input Mapping
1. **ID and Severity**: `FR-BACK-001` | **MEDIUM**
2. **Category**: Backend / Validation
3. **Location**: `flexirule/ruleflow/core/action_handlers/document_action.py:220`
4. **Evidence**: `input_mapping` expressions are evaluated at runtime via `_safe_eval` without checking at compile time whether expression variable roots match declared execution context keys (`doc`, `vars`, `session`).
5. **Impact**: Misconfigured expressions only fail during live rule execution rather than at rule save/validation time.
6. **Root Cause**: AST validation checks for illegal dunder/imports but does not validate context identifier roots during compile time.
7. **Native Frappe Alternative**: Validate identifiers against AST node names using `ast.walk()`.
8. **Version Compatibility**: Python standard library AST.
9. **Recommendation**: Add compile-time check in `validation_service.py` verifying identifier roots against allowed context variables.
10. **Tests**: Add test in `test_validation_service.py`.
11. **Confidence**: Confirmed (Open).

## 4. Native Frappe Framework API Comparison Matrix

| Area | FlexiRule Custom Implementation | Native Frappe Alternative | Recommendation & Decision |
| :--- | :--- | :--- | :--- |
| **Expression AST Validation** | Custom `SafeEvalVisitor(ast.NodeVisitor)` | `frappe.safe_eval()` | **Retain Custom**: Native `safe_eval` uses RestrictedPython which modifies execution semantics; custom AST visitor provides targeted dunder/import security without execution overhead. |
| **Active Version Locking** | `frappe.get_all("Rule", filters=...)` without lock | `frappe.qb.from_("tabRule").where(...).for_update()` | **Adopt Native**: Replace `frappe.get_all` in `validate_single_active_version` with Query Builder `.for_update()` to prevent concurrent active rule race conditions. |
| **Action Plan Caching** | Direct pattern deletion | `frappe.cache.delete_value()` / `delete_keys()` | **Retain Native**: Native Frappe CacheManager ensures compatibility across Redis standalone and cluster environments. |
| **Jinja Context Sanitization** | Explicit dictionary context scoping in `_render_scalar` | `frappe.render_template(..., is_safe=True)` | **Retain Custom Context**: Explicit context scope (`doc` and `vars`) guarantees SSTI protection across all template evaluation paths. |
| **Child Table Appends** | Sequential `doc.append()` loop | `doc.set(table_field, row_list)` | **Adopt Native**: Batch child table row payloads into single `doc.set()` call to eliminate N+1 metadata resolution calls. |
| **Workspace Custom Docs** | `hide_custom: 1` in `ruleflow.json` | Frappe `hide_custom` field | **Leverage Native**: Native Frappe setting cleanly prevents custom doctypes from polluting standard module workspace. |
