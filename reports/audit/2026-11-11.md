## 2. Review of Recent Changes (`81929a2`)

Commit `81929a2` modified `flexirule/ruleflow/workspace/ruleflow/ruleflow.json` to set `"hide_custom": 1`.
- **Architectural Analysis**: In Frappe Framework, when a workspace has `hide_custom: 0` (the default), `frappe.desk.desktop.get_custom_reports_and_doctypes()` appends a auto-generated "Custom Documents" card containing all DocTypes marked `custom: 1, istable: 0` assigned to that workspace module.
- **Verification**: Setting `hide_custom: 1` cleanly suppresses this behavior, ensuring test-generated DocTypes (such as `FRX_TEST_PROCESS_*`) or user-defined custom doctypes do not pollute the production RuleFlow desk workspace.
- **Frappe Compatibility**: `hide_custom` is supported across Frappe v14, v15, and v16. Test suite `flexirule.ruleflow.tests.test_workspace` was executed and passed with 3/3 tests.

## 3. Evidence-Backed Findings Detail

### Finding FR-DATA-002: Active Version Race Condition in `validate_single_active_version`
1. **ID and Severity**: `FR-DATA-002` | **MEDIUM**
2. **Category**: Data Integrity / Concurrency
3. **Location**: `flexirule/ruleflow/doctype/rule/rule.py:1874-1906` (`validate_single_active_version`)
4. **Evidence**: `validate_single_active_version` queries existing active rules using `frappe.get_all("Rule", filters={"base_rule_name": self.base_rule_name, "is_active": 1, ...})`.
5. **Impact**: Under concurrent activation requests for different versions in the same lineage, two transactions can both pass validation before committing, violating the invariant that only one version per lineage may be active simultaneously.
6. **Root Cause**: `frappe.get_all` performs a non-locking `SELECT` query rather than an exclusive row lock (`SELECT ... FOR UPDATE`).
7. **Native Frappe Alternative**: Use Frappe Query Builder (`frappe.qb`) with `.for_update()`:
   ```python
   Rule = frappe.qb.DocType("Rule")
   query = (
       frappe.qb.from_(Rule)
       .select(Rule.name)
       .where((Rule.base_rule_name == self.base_rule_name) & (Rule.is_active == 1) & (Rule.name != self.name))
       .limit(1)
       .for_update()
   )
   existing_active = query.run(pluck=True)
   ```
8. **Version Compatibility**: Frappe v15 and v16 fully support `frappe.qb` with `.for_update()`.
9. **Recommendation**: Replace `frappe.get_all` with `frappe.qb.from_(Rule)...for_update()` inside `validate_single_active_version`.
10. **Tests**: Covered in `test_rule_versioning.py`; additional concurrent race condition integration test recommended.
11. **Confidence**: Confirmed (Open).

### Finding FR-SEC-004: Background Worker Execution Defaults to Administrator Context
1. **ID and Severity**: `FR-SEC-004` | **HIGH**
2. **Category**: Security / Authorization
3. **Location**: `flexirule/ruleflow/core/permissions.py:136-155`
4. **Evidence**: In queued/background Rule executions, background jobs default to `Administrator` session unless the triggering user context is explicitly set via `frappe.set_user(context.user)`.
5. **Impact**: Background rule execution can inadvertently bypass user permission checks or execute operations that the original triggering user had no permission to perform.
6. **Root Cause**: Asynchronous background jobs in Frappe run under worker session defaults (`Administrator`).
7. **Native Frappe Alternative**: Utilize `frappe.set_user(user)` within background job initialization or pass authenticated user session into `frappe.enqueue(..., user=...)`.
8. **Version Compatibility**: Frappe v15 / v16.
9. **Recommendation**: Pass `calling_user` in the background job payload and call `frappe.set_user(calling_user)` during engine worker bootstrap.
10. **Tests**: `test_permissions.py`.
11. **Confidence**: Confirmed (Open).

### Finding FR-PERF-001: N+1 Query Pattern in Child Table Appends
1. **ID and Severity**: `FR-PERF-001` | **HIGH**
2. **Category**: Performance
3. **Location**: `flexirule/ruleflow/core/action_handlers/document_action.py:545-584` (`_apply_table_mappings`)
4. **Evidence**: Iterates over row items calling `doc.append(table_field, row_payload)` individually for each mapped row.
5. **Impact**: For child tables with hundreds of rows, individual row validation and schema lookups introduce high CPU and DB overhead.
6. **Root Cause**: `Document.append()` triggers row-level meta resolution and child table initialization on every invocation.
7. **Native Frappe Alternative**: Batch payload preparation into a single list assign (`doc.set(table_field, row_list)`) or optimized child table bulk extend.
8. **Version Compatibility**: Frappe v15 / v16.
9. **Recommendation**: Construct list of child dict payloads and populate via single `doc.extend()` or `doc.set()`.
10. **Tests**: Benchmark tests in `test_document_action.py`.
11. **Confidence**: Confirmed (Open).

---

### Finding FR-FE-002: Double Stringification of `condition_json`
1. **ID and Severity**: `FR-FE-002` | **MEDIUM**
2. **Category**: Frontend / Contract Drift
3. **Location**: `flexirule/public/js/flexirule/rule_builder/stores/useRuleStore.js:320-340`
4. **Evidence**: `condition_json` is serialized via `JSON.stringify()` in the frontend store before payload submission, but backend controller also attempts `json.dumps()` if passed an object, causing escaped JSON string values stored in DB.
5. **Impact**: Escaped JSON strings stored in database require double `json.loads()` on backend.
6. **Root Cause**: Lack of single clear ownership contract for JSON field serialization between frontend store and Frappe Document controller.
7. **Native Frappe Alternative**: Frappe JSON field auto-parsing (`doc.condition_json`).
8. **Version Compatibility**: Frappe v15 / v16.
9. **Recommendation**: Ensure frontend submits raw object/dict for JSON fields or standardize on single JSON string payload contract.
10. **Tests**: `tests/frontend/flexirule/rule_builder/utils/stable_serialization.test.mjs`.
11. **Confidence**: Confirmed (Open).

## 4. Native Frappe Framework API Comparison Matrix

| Area | FlexiRule Implementation | Native Frappe Alternative | Recommendation & Decision |
| :--- | :--- | :--- | :--- |
| **Expression AST Validation** | Custom `SafeEvalVisitor(ast.NodeVisitor)` | `frappe.safe_eval()` | **Retain Custom**: Native `safe_eval` uses RestrictedPython which alters execution semantics; custom AST visitor provides domain-specific dunder and import security without execution overhead. |
| **Active Version Locking** | `frappe.get_all("Rule", filters=...)` without lock | `frappe.qb.from_(Rule).where(...).for_update()` | **Adopt Native**: Replace `frappe.get_all` in `validate_single_active_version` with Query Builder `.for_update()` to prevent concurrent active rule race conditions. |
| **Action Plan Caching** | Redis key pattern deletion | `frappe.cache.delete_value()` / `delete_keys()` | **Adopt Native**: Standardized on native Frappe CacheManager API to ensure compatibility with Redis cluster environments. |
| **Jinja Context Sanitization** | Manual dictionary context stripping in `_render_scalar` | `frappe.render_template(..., is_safe=True)` | **Retain Custom Context**: Explicit context scope (`doc` and `vars`) guarantees SSTI protection across all Jinja evaluation points. |
| **Child Table Appends** | Sequential `doc.append()` loop | `doc.set(table_field, row_list)` | **Adopt Native**: Batch child table row payloads into a single `doc.set()` call to eliminate N+1 metadata resolution calls. |
| **Workspace Custom Docs** | `hide_custom: 1` in `ruleflow.json` | Frappe `hide_custom` field | **Leverage Native**: Native Frappe feature prevents custom doctypes from polluting standard module workspace. |
