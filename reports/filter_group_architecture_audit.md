# Deep Architecture Audit: FilterGroup Operators vs. Native Frappe

This document presents a comprehensive, deep architectural analysis comparing the FilterGroup / condition systems in **FlexiRule** against the native **Frappe Framework** database filtering mechanics. It details structural flows, evaluates semantic and JSON compatibility, highlights edge cases, and provides a low-risk, future-proof implementation blueprint.

---

## 1. Structural Context & Core Pipelines

FlexiRule handles conditions and criteria in two separate systems, each conceptually doing "filtering" or "criteria evaluation" but under different execution environments:

### Pipeline A: Native Frappe (Database-bound SQL Engine)
1. **Entrypoint:** `frappe.get_list()` / `frappe.get_all()` → `frappe.model.db_query.DatabaseQuery`.
2. **Filter Normalization:**
   - Filters are input as nested dictionaries `{"fieldname": "value"}`, list-of-lists `[["fieldname", "operator", "value"]]` or 4-tuples `[["DocType", "fieldname", "operator", "value"]]`.
   - `frappe.utils.data.get_filter` parses this payload, validates field existence, sanitizes column names, and checks if the operator is in a whitelisted list of valid operators.
3. **Condition Generation (`db_query.py:prepare_filter_condition`):**
   - Resolves Nested Set Operators (`descendants of`, `ancestors of`, etc.) into dynamic lists of matched nodes by running recursive left/right index bounds queries on the tree structures, then automatically rewrites the condition operator to `in` or `not in`.
   - Converts `previous`, `next`, and `timespan` operators to `between` using `get_date_range()`.
   - Maps the `is` operator (`is set` / `is not set`) to standard `=` or `!=` SQL statements after customizing fallback variables.
   - Standardizes database-specific formatting (e.g. `format_date` / `format_datetime`) and wraps nullable columns in index-safe `ifnull()` / `coalesce` structures where applicable.
4. **Final SQL Clause Construction:** Builds the raw database WHERE clause using parameterized bindings.

### Pipeline B: FlexiRule DB Filters (FilterGroup / Query Records)
1. **Frontend Construction:**
   - Generated by `FilterGroup.vue` inside `QueryRecordsConfig.vue`.
   - Defines operators statically on the client using list variables (`BASE_QUERY_OPERATORS`, `QUERY_EXTENSION_OPERATORS`) and invalidity maps (`FRAPPE_INVALID_CONDITION_MAP`).
   - Serializes into structural arrays of the form `[ [doctype, field, operator, value], ... ]`.
2. **Backend Context Resolution (`QueryRecordsHandler`):**
   - Inside `query_records.py:self._resolve_query_filters`, each filter item's `value` is resolved.
   - Evaluates variables (`{vars.my_variable}`), formula expressions, and custom resolver callbacks to flatten them to standard primitive structures.
   - Triggers `_normalize_filters_for_backend()` to clean, map, and translate UI elements to Frappe-safe criteria.
3. **Operator Normalization (`_normalize_single_filter_operator`):**
   - Maps custom/extended UI operators to standard Frappe equivalents:
     - `starts with` → `like`, value serialized as `value%`.
     - `ends with` → `like`, value serialized as `%value`.
     - `Between` → `between`.
     - `Timespan` → resolves relative timespan keywords (e.g. `last week`, `next quarter`) into static datetime ranges on the backend, converting the operator to `between`.
4. **Execution:**
   - Runs either direct Query Builder (Pypika) filters (such as `_apply_qb_filters` which maps `=`, `!=`, `like`, `in`, `between`, and `is` explicitly) or delegates execution to standard `frappe.get_list(filters=...)`.

### Pipeline C: FlexiRule Rule Conditions (In-Memory Python Evaluation Engine)
1. **Frontend Construction:**
   - Constructed via `ConditionBuilder.vue` + `SimpleCondition.vue`.
   - Fetches available operators and their display names from the backend using the whitelisted API endpoint `flexirule.ruleflow.api.get_operator_config()`.
   - Emits deeply nested condition logic structures (logical groups joined by AND/OR).
2. **Backend Compilation (`ConditionCompiler` in `compiler.py`):**
   - Transpiles the condition structure into a safe Python expression string.
   - Translates unary operators like `is_set`, `is_not_set`, `is_empty`, `is_not_empty` directly into logical expression sub-trees.
   - Emits helper calls like `check_link_match` for comparing Link / Dynamic Link fields against multi-element tuples.
3. **Backend Evaluation (`ConditionEvaluator` in `evaluator.py`):**
   - Interpets JSON-based conditions or compiles the Python string and evaluates it inside a sandboxed environment against current document structures in memory.

## 3. Semantic Divergence & Compatibility Analysis

While operator names are mostly similar, execution semantics diverge significantly between SQL (database) execution and Python (in-memory) execution:

### 1. Case Sensitivity & LIKE Queries
- **Frappe SQL (`like` / `not like`):** Matches database collation. On standard MariaDB/MySQL, SQL `LIKE` is **case-insensitive**. On PostgreSQL, Frappe translates `like` to `ilike` inside `db_query.py` to preserve case-insensitivity. Wildcard characters (`%` and `_`) are evaluated natively.
- **FlexiRule In-Memory (`contains`):** Evaluated strictly as `rhs in str(lhs)`. In Python, this check is **case-sensitive** by default.
- **Gap:** A condition checking if Description "contains" "Apple" returns `False` for "Red apple" in-memory, whereas a DB Query for `like "%Apple%"` on MySQL returns `True`.

### 2. Null and Empty Evaluation
- **Frappe SQL:** Wrap nullable columns in `ifnull()` / `coalesce` helper checks. The `is` operator evaluates `set` and `not set` strictly.
- **FlexiRule In-Memory (`is_set` / `is_not_set`):** Evaluates `lhs is not None and lhs != ''` and `lhs is None or lhs == ''`.
- **Parity:** High consistency. Both platforms interpret empty strings and null elements symmetrically.

### 3. Timespan Resolving
- **Frappe SQL:** Uses `get_date_range()` on the backend to dynamically parse relative filters (e.g. `this month`) on query execution.
- **FlexiRule DB:** Hardcodes an identical, but parallel calculation pipeline inside `query_records.py` (`_resolve_timespan_range`).
- **Gap:** Introduces duplicate logic. If Frappe adds a new relative timespan option or updates its calculations, FlexiRule will drift out of sync.

### 4. Tree Hierarchies & Nested Set Operators
- **Frappe SQL:** Parses tree parents and children recursively using left/right indexes (`lft`, `rgt`).
- **FlexiRule DB (Direct Query Builder):** Since the direct PyPika route in `QueryRecordsHandler` only supports standard math operators and ignores tree operations, any tree-based query generated via PyPika will completely fail to evaluate tree relationships.
- **Gap:** Major execution gap under direct PyPika pipelines.

## 4. Architectural Analysis: UI Inconsistencies & Scattered Knowledge

### Current State Architectural Pain Points:
1. **Duplicate Operator Metadata:**
   - Valid operator lists for each fieldtype are hardcoded in Vue (`FilterGroup.vue:FRAPPE_INVALID_CONDITION_MAP`) and duplicate those compiled on the backend (`ConditionCompiler.FIELDTYPE_OPERATORS` in Python).
2. **Brittle Validations:**
   - Client-side validation relies on hardcoded string checks. If a new field type is introduced or custom operators are registered via Frappe hooks, the UI remains unaware until code is updated across both projects.
3. **Implicit Behaviors:**
   - UI input styling (e.g. showing dual fields for `Between` or MultiSelect arrays for `In`) is coupled to hardcoded string comparisons inside Vue instead of being derived dynamically.

## 5. Proposed Future-Proof Layered Operator Architecture

We propose introducing a clean, unified, and backward-compatible **Layered Operator Architecture** that consolidates all filtering knowledge into a single source of truth:

```
┌─────────────────────────────────────────────────────────┐
│                 Operator Definition Layer               │
│               (Central Registry in Python)              │
└────────────────────────────┬────────────────────────────┘
                             │
            Exposes Registry Config over API
                             │
                             ▼
┌─────────────────────────────────────────────────────────┐
│                     Data-Driven UI                      │
│        (FilterGroup.vue / ConditionBuilder.vue)         │
└────────────────────────────┬────────────────────────────┘
                             │
                 Submits Structured JSON
                             │
                             ▼
┌─────────────────────────────────────────────────────────┐
│                    Execution Adapters                   │
│        (SQL/Pypika Adapter & Python Evaluator)          │
└─────────────────────────────────────────────────────────┘
```

### Layer 1: Operator Definition Layer (Central Registry)
Create a centralized registry in `flexirule/ruleflow/core/operators.py` that maps all operators and their characteristics. Every operator is declared with metadata defining its field-type constraints, value types, and whether it is a FlexiRule extension:

```python
class OperatorDefinition:
    key: str                    # Unique ID (e.g., "starts_with", "between")
    label: str                  # Frontend display name
    requires_value: bool        # Does it require a right-hand-side value?
    is_extension: bool          # True if exclusive to FlexiRule
    supported_fieldtypes: list  # Fieldtypes this applies to (e.g., ["Data", "Link"])
    val_type: str               # "scalar", "list", "range", "keyword"
```

A whitelisted API endpoint, `get_operator_registry_config()`, exposes this unified structure directly to the client.

### Layer 2: Execution Adapters (Compile/Runtime Translators)
The execution handlers map registry keys to target-specific logic cleanly:
- **SQL / PyPika Adapter:**
  - Delegates native operators directly to Frappe's native `DatabaseQuery` pipelines.
  - Intercepts FlexiRule extensions (like `starts with` or `ends with`) and resolves them into database-compatible `like` parameters.
- **Python Evaluator Adapter:**
  - Translates registry operators into sandboxed Python execution methods.
  - Resolves semantic gaps (for example, ensuring case-insensitivity on contains/like checks and supporting link-tuple matches safely).

### Layer 3: Data-Driven UI Layer
- Both `FilterGroup.vue` and `SimpleCondition.vue` query the unified registry endpoint.
- Vue templates dynamically configure layout parameters (such as dual inputs for `Between` or chip badges for `In`) based strictly on `val_type` and `requires_value` properties, removing all hardcoded validation dictionaries.

## 6. Incremental Migration Roadmap

This architecture is designed to be introduced incrementally with zero risk to existing visual rules and active revisions:

### Phase 1: Registry Foundation & Backend Integration (Backward-Compatible)
1. **Define Registry:** Build the `OperatorDefinition` model and centralized registry in Python. Include all native Frappe and custom FlexiRule operators.
2. **API Endpoint:** Implement `get_operator_registry_config()` to expose the definition schema.
3. **Execution Routing:** Update `ConditionCompiler` and `QueryRecordsHandler` to validate operator constraints against the central registry instead of custom maps.

### Phase 2: Refactoring Frontend to Data-Driven Config (UI Modernization)
1. **Client-side Fetching:** Update both condition builders and filter groups to retrieve operator definitions dynamically from the backend registry.
2. **Remove Hardcoded Maps:** Deprecate `FRAPPE_INVALID_CONDITION_MAP` and all client-side hardcoded lists.
3. **Maintain Output Parity:** Ensure that the serialized JSON structures generated on save remain completely identical, preventing any database model or migration updates.

### Phase 3: Optimizing Execution & Semantic Alignment (Engine Cleanup)
1. **Unify Timespan Logic:** Refactor `QueryRecordsHandler` to reuse Frappe's native `get_timespan_date_range()` instead of duplicate date range calculation code.
2. **Address Tree Hierarchy Gaps:** Ensure tree operations (`NestedSetHierarchy`) are fully resolved or gracefully evaluated across all backend execution pipelines.
3. **Exhaustive Testing:** Introduce dedicated integration tests to verify complete semantic alignment across both database execution and in-memory evaluation engines.
